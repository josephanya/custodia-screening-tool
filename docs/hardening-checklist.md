# Custodia Screening Tool — Hardening Checklist

 Every item is tracked here whether or not
it is implemented yet. `[x]` means shipped in this repository, `[ ]` means outstanding, and
`[~]` means partially shipped with the remainder described in the note.

Scope rule for this pass: implement everything that can be done inside the existing
Next.js + Postgres + Prisma stack without new infrastructure (Redis, an IdP, an APM vendor) and
without changing clinical question content that needs sign-off.

---

## P0 — Clinical safety

- [x] **Red flags are no longer collapsed into a single boolean.** Every red flag now carries a
  clinical urgency (`urgent` or `emergency`) instead of only ketoacidosis setting
  `urgentCareRecommended`. Chest pain / shortness of breath is now `emergency`; unhealed foot wound
  and sudden vision loss are `urgent`.
- [x] **Urgency is persisted.** `results.urgency`, `results.urgent_care_recommended` and
  `results.red_flags` are stored, so a nurse can see urgency in the dashboard. Previously urgency
  was computed, returned to the browser, and thrown away.
- [x] **Risk and urgency are separate dimensions.** `classification` (risk) and `urgency`
  (clinical escalation) are independent columns; the dashboard sorts and counts on urgency
  separately from high-risk classification.
- [x] **Urgency drives result copy.** The public result page shows an emergency banner, an urgent
  banner, or nothing, instead of a single hard-coded string.
- [ ] **Red-flag questions for the not-diagnosed branch.** An undiagnosed respondent reporting
  ketoacidosis-type symptoms currently receives routine "re-screen in 12 months" guidance because
  branch A never asks. *Deliberately not implemented:* adding clinical questions to the public
  questionnaire needs clinical sign-off, not an engineering decision. Highest-priority clinical
  follow-up.
- [ ] **Golden clinical test vectors.** Needs a clinically approved CSV of cases and expected
  outputs. Boundary and property tests are in place as an interim measure.
- [ ] **"Unknown" modelled explicitly rather than as points.** `unknown` answers still map to a
  numeric weight. Modelling `POSITIVE / NEGATIVE / UNKNOWN / NOT_APPLICABLE / NOT_ANSWERED` changes
  the scoring semantics and needs clinical review.
- [ ] **Full clinical disposition model** (`RecommendedAction`, `FollowUpStatus`). Depends on the
  case-management model below.

## P0 — Scoring integrity and auditability

- [x] **Single source of truth for scoring rules.** Thresholds, weights, labels and cutoffs live in
  [lib/scoring-rules.ts](../lib/scoring-rules.ts). The scoring engine reads them and the seed writes
  the same objects into `scoring_rule_versions.rules`. The previous duplication (hard-coded
  TypeScript vs. an unrelated JSON blob in the database) is gone.
- [x] **Rule-version drift is impossible.** The API resolves the rule row by the exact branch and
  version number the engine implements, then compares a SHA-256 hash of the canonicalised ruleset
  against the stored hash. Any mismatch fails closed with a 503 and an audit event instead of
  persisting a result labelled with the wrong version.
- [x] **Rule resolution happens inside the write transaction**, so a rule activation cannot race a
  submission.
- [x] **Forensic snapshot on every result.** `results.ruleset_hash` and `results.engine_version`
  record exactly what produced the score; `assessments.questionnaire_version` and
  `assessments.responses_hash` record exactly what was answered.
- [x] **Questionnaire version tracked separately from scoring version.**
- [x] **Explanation trace.** Contributing factors are stored with rule id, label and points, and the
  detail page renders them, so "why was this person high risk" is answerable without reading code.
- [~] **Rule approval lifecycle.** `scoring_rule_versions` now has `status`
  (`draft / in_clinical_review / approved / active / retired`), `approved_by`, `approved_at` and
  `retired_at`, and only `active` rows can score a submission. The review *workflow* (UI, approver
  identity, transitions) is not built.

## P0 — Authentication and session architecture

- [x] **Real server-side sessions.** The deterministic HMAC cookie is replaced by a random 256-bit
  token; only its SHA-256 hash is stored in `nurse_sessions`, with `expires_at`, `revoked_at`,
  `last_seen_at`, `ip_hash` and `user_agent`.
- [x] **Sessions are revocable.** Sign-out revokes the row, so the cookie is dead immediately
  instead of remaining valid until the browser expires it.
- [x] **Password hashing supported.** `NURSE_DASHBOARD_PASSWORD_HASH` accepts a scrypt hash
  (`scrypt$N$r$p$salt$hash`, generated by `npm run auth:hash`). Plaintext
  `NURSE_DASHBOARD_PASSWORD` still works for local development.
- [x] **Timing-safe comparison** for both the password and the session token lookup.
- [x] **Hardened cookies.** `__Host-` prefix in production, `HttpOnly`, `Secure`, `SameSite=Lax`,
  `Path=/`, no `Domain`.
- [x] **Login brute-force protection.** 5 failures per IP per 5 minutes and 30 per hour globally,
  enforced *before* password verification, with audit events for throttled attempts.
- [ ] **Per-user identity and MFA.** Still a single shared password. Needs a `nurse_users` table,
  invite/rotation flow and TOTP or WebAuthn.
- [ ] **RBAC.** No roles or permissions yet — the session model is the prerequisite and is now in
  place.

## P0 — Audit trail

- [x] **`audit_events` table** with action, actor type, actor session, resource type/id, hashed IP,
  user agent, metadata and timestamp.
- [x] **Events recorded:** `login_success`, `login_failure`, `login_throttled`, `login_not_configured`,
  `logout`, `session_expired`, `assessment_created`, `assessment_replayed`,
  `assessment_rate_limited`, `assessment_result_viewed`, `assessment_list_viewed`,
  `assessment_searched`, `assessment_viewed`, `ruleset_mismatch`.
- [x] **IPs are hashed, never stored raw** (HMAC with `AUDIT_HASH_SECRET`).
- [x] **Audit writes never break the request** — failures are logged, not thrown.
- [ ] **Audit retention and tamper-evidence** (append-only role, periodic export, hash chaining).

## P1 — Abuse resistance

- [x] **Distributed rate limiting** backed by Postgres (`rate_limit_counters`), so it works on
  serverless/multi-instance deployments without Redis. Fixed window, atomic
  `INSERT … ON CONFLICT DO UPDATE`.
- [x] **Public submissions limited** per IP (30/hour) and per assessment session (5/hour). The
  per-session limit exists because Nigerian mobile CGNAT puts many legitimate users behind one IP,
  so the IP limit alone is set generously.
- [x] **Result reads limited** (120/hour per IP).
- [x] **Request body size cap** (16 KB) enforced before parsing.
- [x] **Rate limiting runs before expensive work** — before validation, scoring and any write.
- [x] **`Retry-After` returned on 429.**
- [ ] **CAPTCHA / Turnstile escalation** after repeated abuse from one source.
- [ ] **Abuse telemetry and alerting.**

## P1 — Idempotency

- [x] **`Idempotency-Key` header honoured**, stored in `assessments.idempotency_key` with a unique
  index. A replay returns the original result with `200` and `Idempotency-Replayed: true` instead of
  creating a duplicate assessment.
- [x] **Replay is scoped to the submitter.** The key alone is not enough to read back a stored
  result: the caller must match the original assessment session *or* resend answers with the same
  `responses_hash`. Anything else is a `409`, so a reused key cannot disclose another person's
  `assessmentId`, `referenceCode`, or classification. The check runs after validation, and both the
  replay and the conflict are audited with which of the two conditions matched.
- [x] **Retries still work** for the two real cases: the same session resubmitting, and a retry whose
  first response (and therefore its session cookie) never arrived but whose answers are identical.
- [x] **Unique-violation race handled** — a concurrent duplicate returns the winner's result rather
  than a 500, and applies the same scoping check.
- [x] **Client sends a stable key** for the whole submission attempt, so double-clicks, retries and
  flaky mobile connections cannot produce duplicate records.

## P1 — Identifiers

- [x] **Reference codes widened** from 8 hex characters (32 bits) to 12 Crockford base32 characters
  (60 bits), generated from a CSPRNG.
- [x] **Ambiguous characters removed** (`I`, `L`, `O`, `U`) so codes survive being read aloud.
- [x] **Dashboard search is an exact normalised lookup**, not `contains`. Prefix scanning of the
  reference space is no longer possible.
- [x] **Legacy 8-character codes still resolve.**

## P1 — Privacy boundaries

- [x] **WhatsApp handoff carries only the reference code.** The previous message body included the
  classification (`My result was diabetes_high`); it now says only that a screening was completed
  and gives the reference.
- [x] **Public assessment cookie lifetime cut** from 30 days to 24 hours.
- [x] **Data retention job.** `npm run db:retention` anonymises assessment responses older than
  `ASSESSMENT_RETENTION_DAYS` (default 365) while keeping the clinical result, and prunes expired
  sessions and stale rate-limit rows.
- [x] **Anonymisation is recorded** (`assessments.anonymized_at`) and the dashboard labels
  anonymised records instead of showing an empty table.
- [ ] **Scheduled execution of the retention job** (cron / platform scheduler) and a documented
  jurisdiction-specific retention period.
- [ ] **Subject access / deletion request handling.**
- [ ] **Encryption at rest** — a deployment concern; document the managed-Postgres setting in the
  runbook.
- [ ] **Consent record persisted.** The intro checkbox is enforced client-side only and is not
  stored with the assessment.

## P1 — Dashboard scalability

- [x] **Cursor pagination** (50 per page, `orderBy created_at desc, id desc`, keyset cursor). The
  unbounded `findMany` is gone.
- [x] **Narrow `select`** instead of hydrating full assessment + result + rule-version objects.
- [x] **Counts computed in the database** with `count()` aggregates rather than by loading every row
  and calling `.length`.
- [x] **Supporting indexes** on `(created_at desc, id desc)`, `classification`, `urgency`.

## P2 — Transport and browser hardening

- [x] **Security headers** on every response: `Content-Security-Policy`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `X-Frame-Options: DENY`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, and HSTS in
  production.
- [x] **Dashboard responses marked `no-store`** so assessment data is not cached by intermediaries.
- [~] **CSP still allows `'unsafe-inline'` for scripts**, which Next.js requires without a
  per-request nonce. Moving to a nonce-based CSP via `proxy.ts` is the follow-up.
- [ ] **Explicit CSRF strategy.** `SameSite=Lax` plus Next's server-action origin check covers the
  current mutations (sign in, sign out). A token scheme is needed before adding assign / triage /
  export / delete actions.

## P2 — Operability

- [x] **Structured JSON logging** ([lib/logger.ts](../lib/logger.ts)) with event names, durations and
  outcomes. Questionnaire payloads are never logged.
- [x] **Safe error boundaries** on both API routes: typed status codes
  (400 / 404 / 405 / 409 / 413 / 429 / 500 / 503) and a generic client-facing message, with the real
  error only in server logs.
- [x] **No internal detail leaks** — Prisma errors, SQL, stack traces and hostnames never reach the
  client.
- [x] **Health endpoint reports database reachability** instead of returning a static payload.
- [ ] **Metrics and tracing** (OpenTelemetry, `assessment_submissions_total`, scoring latency
  histograms, alerting). Log lines are structured for this but nothing exports them.

## P2 — Delivery

- [x] **CI pipeline** ([.github/workflows/ci.yml](../.github/workflows/ci.yml)): install → Prisma
  generate → lint → typecheck → unit tests → build → dependency audit, plus a migration job that
  applies every migration to a real Postgres service and runs the seed.
- [x] **`npm audit --audit-level=high` passes.** `@prisma/config` pins `deepmerge-ts@7.1.5`, which
  carries GHSA-ggr8-5vv4-36mx (stack exhaustion on recursive object graphs). Prisma 7.9.1 is the
  latest release and has no fix, and `npm audit fix --force` would downgrade to `prisma@6.12.0`. An
  `overrides` entry pins `deepmerge-ts@^8.0.1` instead; the Prisma CLI is verified against it
  (`generate`, `validate`, `migrate deploy` on a fresh database, `migrate diff`, `db seed`). Remove
  the override once Prisma ships a release that bumps the dependency.
- [x] **`npm run typecheck`** added.
- [ ] **Branch protection** (required checks, required review, no force push) — a GitHub settings
  change, not a repository change.
- [ ] **Secret scanning, SAST, container and DAST scanning.**

## P2 — Testing

- [x] **Boundary tests** for every scoring threshold (age 44/45/54/55/64/65, BMI 24.99/25/30/30.01,
  waist 79/80/88/88.01 and 93/94/102/102.01, both cutoffs at n-1 / n).
- [x] **Property test:** adding a risk factor can never decrease the score.
- [x] **Red-flag tests** covering classification override, urgency mapping and precedence over the
  weighted checklist.
- [x] **Ruleset hash regression test** — the hash is pinned, so any change to a clinical weight
  fails CI until the constant is updated deliberately.
- [x] **Reference-code tests** for format, entropy alphabet, and normalisation of legacy, lowercase,
  spaced and prefix-less input.
- [x] **Rate-limit window arithmetic tests.**
- [ ] **API / persistence / security integration tests.** Need a test database harness; the CI
  migration job is the foundation.

## P3 — Architecture

- [ ] **Layer separation** (`domain/`, `application/`, `infrastructure/`). Business logic is
  isolated in `lib/` but the route handler still orchestrates directly.
- [ ] **Case management model** (`Case` with status, assignee, priority, contact attempts, notes as
  individually auditable rows — never inside the responses JSON).
- [ ] **Structured clinical columns** alongside the immutable responses snapshot.
- [ ] **`sex` renamed to `sexAtAssessment`** to make the clinical meaning explicit.
- [x] **Stay a modular monolith.** No microservice split.

## Review claims that did not hold

- The review states the red-flag branch returns `redFlags: []` and `urgentCareRecommended: false`.
  It did not — `scoreComplicationRisk` returned early with the populated red-flag list. The real
  defects were narrower and are fixed above: only ketoacidosis set `urgentCareRecommended`, and
  none of the urgency output was ever persisted, so the nurse dashboard could not see it.
- The review states the WhatsApp handoff may carry clinical detail. It carried the classification
  string only, not the questionnaire answers. That has still been removed.
